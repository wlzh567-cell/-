# 입주청소 중심 청소업체 랜딩페이지 PRD

문서 상태: 구현 기준안  
제품 형태: 전환형 랜딩페이지 1장  
기본 기술: Next.js App Router + TypeScript + Tailwind CSS

---

## 1. 프로젝트 개요

### 1.1 목적

입주를 앞둔 고객이 페이지를 방문한 직후 다음 세 가지를 빠르게 이해하도록 한다.

1. 이 업체는 입주청소를 중심으로 공간을 정돈하는 청소업체다.
2. 어떤 공간과 항목을 상담할 수 있는지 알 수 있다.
3. 부담 없이 견적 문의 정보를 입력할 수 있다.

페이지의 핵심 흐름은 다음과 같다.

`첫인상 → 입주청소 가치 이해 → 결과 비주얼 → 서비스 범위 확인 → 진행 방식 이해 → 견적 문의`

### 1.2 핵심 성공 조건

- 첫 화면에서 5초 안에 `입주청소`, `새 공간의 시작`, `견적 받기`가 인지된다.
- 입주청소가 보조 서비스보다 명확히 큰 비중으로 보인다.
- 실제 근거가 없는 숫자·후기 없이도 프로세스와 정보 설계로 신뢰를 만든다.
- 모바일에서 CTA와 폼 사용이 편하다.
- 문의 폼은 입력 검증만 수행하며 실제로 접수된 것처럼 오해시키지 않는다.

### 1.3 목표 행동

주요 행동은 `견적 받기` 버튼을 눌러 페이지 하단의 문의 폼으로 이동하고 필요한 정보를 입력하는 것이다.

초기 버전에서는 네트워크 전송을 하지 않는다. 유효성 검증을 통과하면 다음과 같이 안내한다.

> 입력 형식이 확인되었습니다. 현재는 데모 단계로 실제 견적 요청이 접수되거나 저장되지 않습니다.

### 1.4 비목표

- 실제 견적 계산 또는 가격표 제공
- 실시간 예약, 일정 확정, 결제
- API, 데이터베이스, 관리자 페이지
- 로그인, 회원가입, 마이페이지
- 이메일, 문자, 카카오톡 전송
- 고객 후기, 작업 통계, 인증을 임의 생성
- 실제 현장으로 오인할 수 있는 가짜 Before/After 제작

## 2. 사업 및 브랜드 방향

### 2.1 서비스 우선순위

- 주력: 입주청소
- 보조: 이사청소, 사무실 청소, 소파 청소, 의자 청소
- 권장 노출 비중: 입주청소 60~70%, 보조 서비스 합계 30~40%

### 2.2 포지셔닝

가격 경쟁을 전면에 내세우는 청소업체가 아니라, 새로운 공간을 편안하게 시작할 수 있도록 준비하는 전문 서비스로 인식되어야 한다.

핵심 인상:

- 정돈됨
- 명확함
- 세심함
- 부담 없는 상담
- 현대적인 전문성

### 2.3 브랜드 한 문장

> 새로운 공간의 시작을, 깨끗하게 준비합니다.

회사명은 미정이다. 구현 시 가짜 상호를 만들지 말고 헤더 워드마크에는 임시로 `입주청소 전문`을 사용한다. 사용자가 상호를 제공하면 한 곳의 설정값만 바꿔 전체에 반영되도록 구성한다.

### 2.4 톤앤매너

- 친절하지만 과장하지 않는다.
- 전문적이지만 딱딱하지 않는다.
- 짧은 문장과 충분한 여백으로 읽는 부담을 줄인다.
- `최저가`, `완벽`, `100%`, `업계 1위` 같은 검증 불가능한 표현은 쓰지 않는다.

## 3. 핵심 사용자

### 3.1 입주 예정 개인 고객

- 상황: 아파트, 빌라, 오피스텔 등 새 공간으로 이사할 예정
- 궁금한 점: 어디까지 청소하는지, 우리 공간도 가능한지, 상담은 무엇을 준비해야 하는지
- 걱정: 보이지 않는 곳의 오염, 불명확한 범위, 과장 광고, 견적 문의의 번거로움

### 3.2 이사 전후 고객

- 상황: 기존 공간을 정리하거나 새 거주자를 맞을 준비가 필요
- 필요한 정보: 공간 유형, 희망 일정, 요청 범위를 전달하는 쉬운 방법

### 3.3 사업장 담당자

- 상황: 사무실 또는 다량의 패브릭 의자·소파 청소를 검토
- 필요한 정보: 여러 품목 또는 공간도 상담 가능하다는 사실과 문의 경로

## 5. 섹션별 요구사항

### 5.1 고정 헤더

목적: 브랜드 역할과 핵심 이동 경로를 간결하게 제공한다.

구성:

- 왼쪽: 임시 워드마크 `입주청소 전문`
- 데스크톱 내비게이션: `입주청소`, `서비스`, `진행 안내`, `FAQ`
- 오른쪽 주요 CTA: `견적 받기`
- 모바일: 간결한 워드마크와 `견적 받기` 버튼을 우선하고, 필요할 때만 접근 가능한 메뉴를 둔다.

요구사항:

- 스크롤 시 얇은 배경과 구분선으로 콘텐츠와 분리한다.
- CTA는 `#quote`로 부드럽게 이동한다.
- 키보드 포커스가 분명해야 한다.

### 5.2 히어로

목적: 무엇을 제공하는지 즉시 이해시키고 첫 CTA를 만든다.

권장 카피:

Eyebrow:

> 입주 전 마지막 준비

Headline:

> 새로운 공간의 시작은,  
> 깨끗함부터.

Body:

> 아파트부터 오피스텔까지, 입주를 앞둔 공간의 청소 범위를 함께 확인하고 필요한 준비를 안내합니다.

CTA:

- Primary: `견적 받기`
- Secondary text link: `서비스 살펴보기`

비주얼:

- 밝고 정돈된 실내의 넓은 결과 이미지를 우선한다.
- 검증된 실제 사진이 없다면 일반 또는 생성 이미지를 실제 사례로 표현하지 않는다.
- 비실사 대체안으로 빛, 표면, 창, 정돈된 공간을 추상화한 자체 비주얼을 사용할 수 있다.
- 일반·생성 이미지를 쓰면 가까운 곳에 `서비스 이해를 돕기 위한 연출 이미지`를 표시한다.

### 5.3 입주청소 핵심 가치

목적: 숫자와 후기 대신 사용자가 이해할 수 있는 청소 관점으로 신뢰를 만든다.

권장 제목:

> 생활을 시작하기 전,  
> 공간부터 차분히 살핍니다.

다룰 내용:

- 손이 자주 닿는 곳
- 먼지가 머물기 쉬운 틈과 가장자리
- 주방·욕실처럼 사용 전 확인이 필요한 공간

주의:

- 실제 작업 방식이 확정되지 않은 항목을 서비스 보장처럼 단정하지 않는다.
- `상담 시 공간별 요청 범위를 함께 확인합니다`처럼 사실에 안전한 문장을 사용한다.
- 아이콘 카드 3개를 기계적으로 나열하기보다 큰 타이포와 하나의 공간 비주얼을 교차 배치한다.

### 5.4 결과 중심 이미지 스토리

목적: 방문자가 청소 후 공간의 인상을 시각적으로 상상하게 한다.

구성:

- 한 장의 대형 이미지 또는 서로 다른 크기의 2~3장 이미지
- 짧은 캡션: `빛이 닿는 면부터 손이 닿는 곳까지`
- 이미지 성격 표시: `연출 이미지` 또는 `실제 작업 사진` 중 사실에 맞는 하나

실제 사진이 제공되기 전 금지 사항:

- 가짜 Before/After 슬라이더
- `OO동 현장`, `고객님 댁` 등 실제 사례처럼 보이는 캡션
- 오염이 극적으로 사라지는 합성 비교

이미지가 없을 때도 레이아웃이 깨지지 않도록 우아한 뉴트럴 대체 비주얼과 교체 가이드를 제공한다.

### 5.5 입주청소 공간별 범위

목적: 고객이 상담할 범위를 구체적으로 떠올리게 한다.

권장 제목:

> 공간마다 필요한 청소는 다르니까.

탭 또는 접근 가능한 선택 UI:

- 주방
- 욕실
- 방·거실
- 창틀·베란다
- 현관·수납

각 항목은 `상담 가능한 대표 영역`으로 표현한다. 실제 포함 범위와 제외 항목은 사용자 확인 전까지 확정 문구로 쓰지 않는다.

예시 형식:

- 주방: 상·하부장 외부, 조리대, 싱크대 등 상담 시 범위 확인
- 욕실: 세면대, 수전, 타일, 배수구 주변 등 상담 시 범위 확인

`모두 기본 포함`처럼 오해할 표현은 금지한다.

### 5.6 보조 서비스

목적: 입주청소 외 문의도 가능하다는 점을 보여주되 주력 메시지를 흐리지 않는다.

서비스:

1. 이사청소 — 이사 전후 비어 있는 공간의 청소 상담
2. 사무실 청소 — 업무 공간과 공용 공간의 청소 상담
3. 소파 청소 — 소재와 오염 상태를 확인한 뒤 범위 상담
4. 의자 청소 — 사무용·패브릭 의자 등 수량과 소재별 상담

표현 방식:

- 데스크톱에서는 크기가 다른 2×2 또는 가로 스크롤 구성을 사용할 수 있다.
- 모든 카드를 동일하게 반복하기보다 한 서비스에 큰 비주얼, 나머지에는 간결한 텍스트를 사용한다.
- 매트리스, 유리창 등 요청하지 않은 서비스를 자동으로 추가하지 않는다.

### 5.7 상담 진행 흐름

목적: 문의에 대한 심리적 부담을 낮춘다.

초기 버전에서 안전하게 표시할 수 있는 흐름:

1. 공간과 희망 내용을 입력
2. 입력 형식을 화면에서 확인
3. 실제 상담 채널 연결 후 견적 상담 진행 예정

실제 영업 프로세스가 확인되면 교체할 후보:

- 상담 접수
- 공간·범위 확인
- 견적 안내
- 일정 협의

확정 전에는 방문 확정, 가격 확정, 작업 완료를 약속하지 않는다.

### 5.8 견적 문의 폼

목적: 견적 상담에 필요한 최소 정보를 이해하기 쉽게 입력하도록 한다.

필드:

| 필드 | 형식 | 필수 여부 | 검증 |
|---|---|---:|---|
| 서비스 | 선택 | 필수 | 입주청소, 이사청소, 사무실, 소파, 의자, 기타 문의 |
| 공간 유형 | 선택 | 필수 | 아파트, 오피스텔, 빌라·주택, 사무실, 기타 |
| 지역 | 텍스트 | 필수 | 2자 이상, 상세 주소 입력 유도 금지 |
| 면적 또는 수량 | 텍스트 | 선택 | 자유 형식, 예: `84㎡` 또는 `의자 20개` |
| 희망 시기 | 텍스트 또는 날짜 | 선택 | 과거 날짜 방지 시 로컬 기준 사용 |
| 이름 | 텍스트 | 필수 | 2~30자 |
| 연락처 | tel | 필수 | 한국 전화번호의 일반적 숫자·하이픈 형식 허용 |
| 문의 내용 | textarea | 선택 | 최대 500자, 민감정보 입력 금지 안내 |
| 개인정보 안내 동의 | 체크박스 | 필수 | 데모 단계와 미저장 사실을 명확히 설명 |

개인정보 안내 문구 초안:

> 이 화면은 입력 형식 확인용 데모입니다. 입력한 정보는 서버로 전송되거나 저장되지 않습니다. 실제 접수 기능을 연결하기 전 수집 항목, 이용 목적, 보유 기간, 사업자 정보를 확정해야 합니다.

버튼:

- 기본: `입력 내용 확인`
- 처리 중 상태는 네트워크 요청이 없으므로 불필요하게 길게 연출하지 않는다.
- 검증 성공 후: `입력 형식이 확인되었습니다. 실제 접수는 되지 않았습니다.`

동작:

- 모든 검증은 클라이언트에서 수행한다.
- `fetch`, Server Action, 외부 폼 서비스, localStorage, sessionStorage를 사용하지 않는다.
- 성공 시 가짜 접수번호나 완료 화면을 만들지 않는다.
- 오류 메시지는 해당 필드와 연결하고 첫 오류로 포커스를 이동한다.

### 5.9 FAQ

확정 정보가 없어도 답할 수 있는 질문만 사용한다.

권장 질문:

1. 어떤 청소를 문의할 수 있나요?
2. 견적 문의 전에 무엇을 준비하면 되나요?
3. 사진을 함께 전달해도 되나요?
4. 온라인 문의가 바로 접수되나요?

답변은 확정된 사실만 사용한다. 서비스 지역, 가격, 소요 시간, 추가요금, 장비, A/S는 사업자 답변을 받기 전 공개하지 않는다.

### 5.10 푸터

구성:

- 임시 워드마크 `입주청소 전문`
- 한 문장 소개
- 동일 페이지 앵커 링크
- 개인정보 안내 요약
- `회사명, 대표자, 사업자등록번호, 주소, 연락처: 운영 정보 확정 후 반영`이라는 개발용 체크 항목

운영 정보가 미정인 상태에서 가짜 법인·사업자 정보를 표시하지 않는다. 개발용 `TBD`는 공개 UI보다 `docs/decisions.md`에 우선 기록하고, 푸터 UI는 최소한으로 유지한다.

## 6. 비주얼 디자인 시스템

### 6.1 아트 디렉션

키워드: `맑음`, `여백`, `빛`, `표면`, `정돈`, `조용한 자신감`

참고 감성은 토스·애플 계열의 명료한 제품 페이지다. 특정 브랜드의 레이아웃, 카피, 에셋, 아이콘을 복제하지 않는다.

### 6.2 색상 방향

권장 토큰 예시:

- `--background`: 따뜻한 오프화이트
- `--surface`: 순백 또는 아주 옅은 쿨 그레이
- `--text-primary`: 진한 네이비·잉크
- `--text-secondary`: 중간 명도의 블루 그레이
- `--accent`: 깨끗한 청록 또는 맑은 블루 중 한 가지
- `--border`: 낮은 대비의 뉴트럴
- `--error`: 접근성을 만족하는 레드

색상값은 구현 중 대비를 확인해 조정한다. 포인트 색은 CTA와 핵심 상태에 집중한다.

### 6.3 타이포그래피

- 한국어 가독성이 좋은 시스템 폰트 또는 프로젝트에 적합한 합법적 웹폰트
- Hero: 모바일 48px 안팎, 데스크톱 80~96px 범위에서 반응형 조정
- Section title: 모바일 34~42px, 데스크톱 56~72px
- Body: 모바일 최소 16px, 주요 설명 18~22px
- 줄 길이: 본문 기준 약 45~70자 이내
- 지나치게 얇은 폰트 두께는 피한다.

### 6.4 레이아웃

- 최대 콘텐츠 폭 약 1200~1320px
- 모바일 좌우 여백 20~24px
- 데스크톱 섹션 상하 여백 120~180px
- 히어로는 단순 중앙 정렬만 고집하지 않고 텍스트와 결과 비주얼의 비대칭 긴장을 만든다.
- 섹션마다 배경·밀도·정렬에 변화를 주되 전체 리듬은 통일한다.

### 6.5 이미지

우선순위:

1. 사용자가 제공하고 실제 사용 권한이 확인된 작업 사진
2. 사용 권한과 출처가 기록된 일반 공간 이미지
3. 실제 사례로 오인되지 않는 생성·추상 비주얼
4. 교체 가능한 뉴트럴 플레이스홀더

모든 비사용자 제공 이미지는 `docs/decisions.md`에 출처·용도·표시 문구를 기록한다.

### 6.6 모션

- 첫 진입 시 텍스트와 이미지의 10~20px 내외 부드러운 등장
- 스크롤 시 과한 패럴랙스 대신 느린 페이드·마스크 전환
- 버튼 hover와 focus는 즉각적이고 절제되게
- `prefers-reduced-motion: reduce`에서는 비필수 애니메이션을 제거
- 모션 때문에 콘텐츠가 늦게 보이거나 레이아웃이 흔들리지 않게 한다.

## 7. 반응형 요구사항

### 모바일

- 주요 메시지와 CTA가 첫 화면 안에서 인지되어야 한다.
- 폼은 한 열로 구성한다.
- 터치 대상 최소 44×44px를 목표로 한다.
- 하단 고정 CTA를 사용할 경우 폼에 도달하면 겹치지 않게 숨기거나 축소한다.
- 가로 스크롤이 생기지 않아야 한다.

### 태블릿

- 텍스트와 이미지의 2열 전환 시 줄 길이와 터치 영역을 확인한다.
- 카드 수에 맞춰 억지로 4열을 만들지 않는다.

### 데스크톱

- 넓은 여백과 큰 이미지를 적극 활용한다.
- 본문 폭이 지나치게 넓어지지 않게 한다.
- 마우스가 없어도 모든 기능을 사용할 수 있어야 한다.

권장 확인 폭: 360, 390, 768, 1024, 1440px.

## 8. 접근성 요구사항

- 문서당 하나의 명확한 `h1`과 논리적인 헤딩 순서
- `header`, `nav`, `main`, `section`, `footer` 시맨틱 구조
- 건너뛰기 링크 제공
- 모든 입력에 보이는 label 제공
- placeholder를 label 대용으로 쓰지 않음
- 오류 문구와 입력 연결, 오류 요약 또는 첫 오류 포커스
- 색만으로 상태를 전달하지 않음
- 텍스트와 주요 UI는 WCAG AA 수준 대비 목표
- 키보드로 메뉴, 탭, FAQ, 폼 사용 가능
- 이미지 alt는 장식 여부와 목적에 맞게 작성
- 자동 재생 영상과 과도한 모션 사용 금지

## 9. 기술 요구사항

### 9.1 기본 구성

- Next.js 최신 안정 버전의 App Router
- TypeScript strict mode
- Tailwind CSS
- 패키지 매니저는 기존 저장소 설정을 따른다. 새 프로젝트라면 한 종류만 선택하고 lockfile을 유지한다.
- ESLint 및 프로젝트 기본 품질 검사

### 9.2 권장 구조

```text
app/
  layout.tsx
  page.tsx
  globals.css
components/
  layout/
  sections/
  ui/
lib/
  content.ts
  validation.ts
public/
  images/
docs/
  PRD.md
  decisions.md
```

구조는 기존 코드가 있을 경우 그 관례를 우선한다. 작은 페이지에 불필요하게 많은 파일이나 디자인 시스템 계층을 만들지 않는다.

### 9.3 렌더링 및 상호작용

- 정적 콘텐츠는 Server Component 우선
- 폼, 탭, FAQ 등 필요한 범위만 Client Component
- 폼 검증 로직은 테스트 가능한 순수 함수로 분리하는 것을 권장
- 부드러운 앵커 이동은 CSS로 처리하되 reduced-motion을 고려
- 이미지가 있으면 `next/image`로 최적화

### 9.4 SEO 및 메타데이터

확정된 사실만 사용한다.

- 기본 title 예시: `입주청소 전문 | 새로운 공간의 깨끗한 시작`
- description 예시: `입주청소를 중심으로 이사청소, 사무실, 소파, 의자 청소 상담을 안내합니다.`
- canonical, 사업 지역, 전화번호, LocalBusiness 구조화 데이터는 실제 도메인과 정보가 확정된 뒤 추가
- 가짜 평점, 가격대, 영업시간을 구조화 데이터에 넣지 않음

### 9.5 개인정보 및 보안

- 초기 폼 데이터는 서버와 외부 서비스로 전송하지 않는다.
- 브라우저 저장소에도 저장하지 않는다.
- 상세 주소, 주민번호, 출입 비밀번호 등 민감정보 입력을 유도하지 않는다.
- 실제 수집 기능을 연결하기 전 개인정보 처리방침과 동의 문구를 법률·운영 기준에 맞게 별도 검토한다.

### 9.6 성능 목표

- 불필요한 대형 라이브러리와 클라이언트 JavaScript를 줄인다.
- 히어로 주요 이미지에 크기와 우선순위를 적절히 지정한다.
- 레이아웃 이동을 방지한다.
- 목표 참고치: Lighthouse Performance/Accessibility/Best Practices/SEO 각 90 이상. 개발 환경과 이미지 상태에 따라 달라질 수 있으므로 보장 수치로 공개하지 않는다.

## 11. 분석 이벤트 설계안

실제 분석 도구는 초기 범위에서 연결하지 않는다. 추후 연결을 위한 이벤트 이름만 주석 또는 문서에 정의할 수 있다.

- `quote_cta_click`
- `service_view`
- `quote_form_start`
- `quote_form_validation_success`
- `quote_form_error`

개인정보, 이름, 전화번호, 문의 본문은 분석 이벤트에 포함하지 않는다.

## 13. 수용 기준

### 디자인

- [ ] 첫 화면에서 입주청소와 `견적 받기`가 즉시 보인다.
- [ ] 큰 한국어 타이포, 넓은 여백, 결과 중심 비주얼이 구현됐다.
- [ ] 카드 반복에 의존하지 않고 섹션별 시각적 리듬이 있다.
- [ ] 모바일 360px부터 데스크톱 1440px까지 레이아웃이 안정적이다.
- [ ] 특정 브랜드를 복제하지 않았다.

### 콘텐츠와 사실성

- [ ] 입주청소 비중이 가장 크다.
- [ ] 이사청소, 사무실, 소파, 의자 청소가 보조로 소개된다.
- [ ] 가짜 고객, 후기, 가격, 연락처, 작업 건수, 인증이 없다.
- [ ] 일반·생성 이미지는 실제 작업 사진으로 오인되지 않게 표시됐다.
- [ ] 미정 사업 정보가 `docs/decisions.md`에 기록됐다.

### 기능

- [ ] 모든 주요 CTA가 `#quote` 또는 의도한 섹션으로 이동한다.
- [ ] 폼 필수값, 형식, 글자 수 검증이 작동한다.
- [ ] 폼 데이터가 전송·저장되지 않는다.
- [ ] 성공 상태에 실제 미접수 사실이 명확히 표시된다.
- [ ] FAQ와 선택 UI를 키보드로 사용할 수 있다.

### 품질

- [ ] 프로덕션 빌드가 통과한다.
- [ ] TypeScript 검사와 린트가 통과한다.
- [ ] 콘솔 오류와 깨진 링크가 없다.
- [ ] 키보드 포커스와 reduced-motion을 확인했다.
- [ ] 검증 결과와 남은 TBD가 최종 보고에 포함됐다.
